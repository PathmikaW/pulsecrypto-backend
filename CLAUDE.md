# pulsecrypto-backend — Instructions for Claude Code

PulseCrypto's backend: a Node.js/Fastify/`ws` gateway that ingests live Binance market
streams, conflates them, and broadcasts processed updates to the mobile app.

**This repo follows Spec-Driven Development.** Before implementing any unit of work, read
its spec in `specs/`. If no spec exists for what you're about to build, stop and write the
spec first (or ask) — do not implement directly from this file or from memory of the ADR.

## Session start protocol — run this before anything else (ADR-X6)

**Do this at the start of every session — a brand-new one, one resumed after context
compaction, or one picking this project back up after any gap.** Do not skip it because a
conversation summary already describes this project — a summary can be wrong, stale, or
have lost fidelity in ways that are invisible until they cause a mistake. This has already
happened once on this project (an initial Gitflow bootstrap produced a rootless commit
because a risk was noticed and not acted on) — this protocol exists specifically because of
that, not as generic caution.

1. **Read this entire `CLAUDE.md` file** — not just the section that looks relevant to the
   immediate task.
2. **Read the specific `specs/*.md` file(s) the task actually touches**, in full.
3. **Check real current repository state with direct commands before assuming anything:**
   `git status`, `git log --oneline --all --graph`, `git ls-remote origin` if remote state
   matters to the task, and `ls`/file reads for anything about to be modified. Never
   proceed on a conversation summary's account of what state things are in when a direct
   check is cheap and available.
4. **If real state doesn't match what `CLAUDE.md`/`specs`/the ADR describe** (scaffold
   missing, unexpected branch structure, a file that should exist doesn't) — stop and flag
   the discrepancy to the user. Don't silently "fix" it into whatever seems reasonable, and
   don't proceed as if the mismatch weren't there.
5. **Before declaring any structural task done — git topology, folder/dependency
   architecture, schema changes, anything that touches more than one file in a coordinated
   way — verify the actual resulting state directly** (`git log --graph`,
   `git merge-base --is-ancestor`, re-reading the changed files, whatever directly confirms
   the real outcome). Don't infer success from individual step outputs looking correct in
   sequence — that's exactly how the rootless-commit mistake happened: each `git checkout -b`
   reported success, and the aggregate result was still wrong.
6. **If a risk or edge case becomes apparent mid-task, resolve it before finishing, or say
   it out loud explicitly.** Noticing a problem and silently proceeding as if it were
   handled is a worse outcome than not noticing it — it creates the appearance of care
   without the substance of it. Full rationale: ADR-X6 in
   `docs/adr/03-cross-cutting-decisions.md` (grep for `ADR-X6`, don't read the whole file).

## Framework scaffolding — never done by Claude Code (ADR-X5)

**The initial project scaffold is generated by the user, manually, in their own terminal,
using `pnpm create fastify`** — invokes `create-fastify`
(`github.com/fastify/create-fastify`), Fastify's own official generator (this was checked
twice with two different results — Fastify's main Getting Started guide shows no
generator, but `create-fastify` is a real, separately-documented official one; see ADR-X5
for the full correction trail, kept rather than silently fixed). Not `pnpm init` (that only
creates a bare `package.json`, no generator). **Package manager is pnpm** (ADR-X5 — chosen
explicitly over npm/Yarn, see `docs/adr/03-cross-cutting-decisions.md`). This is not something a Claude
Code session does on the user's behalf, even if asked to "set up the project" — if this
repo is empty or missing its scaffold, stop and say so; don't generate
`package.json`/`tsconfig.json`/an app skeleton to "get started." The user verifies the
scaffold builds and runs before any feature work begins.

**What this does NOT cover:** once the verified scaffold exists, routine dependency
installs during feature implementation (`pnpm add <package>` for something a spec calls
for) are normal work and fine to run directly — the boundary is specifically the _initial
scaffold_, not every subsequent install. See ADR-X5 in the ADR for the full reasoning and
this same boundary stated for the mobile repo.

## Evaluation context — why "correct-enough" isn't the bar here

This is a practical assignment. The reviewer is
evaluating the architecture, the specific decisions made and their rationale, and code
quality — not only whether the app runs. Concretely, this means:

- Follow the stated architecture **literally**, not "in spirit." A dependency-direction
  violation or a reintroduced-and-rejected pattern (e.g. a second backpressure mechanism)
  is a worse outcome than slower progress.
- Use idiomatic, industry-standard patterns for whatever library is in play (idiomatic
  Fastify plugin structure, idiomatic Zod schema composition, idiomatic Vitest test
  structure) rather than code that merely works. If you're unsure what's idiomatic for a
  given library, say so rather than guessing.
- Never take a shortcut that would make the code or the decision look worse under review
  to save time now — flag the tension and ask instead of silently choosing "fast" over
  "correct as specified."
- Tests and specs are not optional scaffolding to skip when a deadline feels close — the
  testing strategy itself is part of what's being evaluated.

## Branching (ADR-X2 — Gitflow)

Never commit directly to `main` or `develop`.

- `develop` is the integration branch. All day-to-day work happens on a `feature/*` (new functionality) or `fix/*` (bug fix) branch
  cut **from `develop`**, e.g. `feature/binance-pair-resolver`,
  `feature/websocket-backpressure`, `feature/pairs-meta-endpoint`. PR back into `develop`,
  squash merge.
- `main` only ever receives merges from a `release/*` or `hotfix/*` branch — never a
  feature branch directly, and never a direct commit.
- `release/*` branches (e.g. `release/v1.0.0`) cut from `develop` when a set of features is
  ready to stabilize. Only bug fixes land on a release branch, no new feature work. On
  completion, merge into both `main` (tag it) and back into `develop`.
- `hotfix/*` branches (e.g. `hotfix/reconnection-timeout`) cut from `main` for an urgent
  fix to already-released code. Merge into both `main` (tag it) and `develop`.
- If you're not sure whether something is a `feature/*`, `fix/*`, `release/*`, or `hotfix/*` — it's
  almost always `feature/*`, cut from `develop`. `release/*` and `hotfix/*` are for the
  specific stabilization/patch scenarios above, not a default choice.

## Non-negotiable architectural constraints

These are decisions that were already debated and settled in the ADR (including cases
where a more elaborate approach was deliberately rejected). Do not silently re-introduce
a rejected alternative because it looks more "robust" — if you think a constraint below is
actually wrong, say so and ask, don't just build the other thing.

**Dependency direction (ADR-B7) is enforced, not aspirational:**

- `domain/` imports nothing outside `domain/`.
- `application/` imports only `domain/`.
- `infrastructure/` implements `domain/` ports; only `server.ts` (composition root) imports
  it. `api/` depends on `application/` only, never on `infrastructure/`; anything an
  `api/` route needs from infrastructure (e.g. the metrics exporter) is injected by `server.ts`.
- `server.ts` is the only file that instantiates concrete `infrastructure/` classes.
- If you're about to import `infrastructure/` from `domain/` or `application/`, stop.

**Pair resolution (ADR-B3) — exact logic, not approximate:**

- The five required pairs (`REQUIRED_PAIRS` env var) are ALWAYS included, unconditionally,
  regardless of what dynamic resolution does.
- Additional pairs: query `exchangeInfo` + `ticker/24hr`, filter to
  `status=TRADING && quoteAsset=USDT && isSpotTradingAllowed`, exclude leveraged tokens
  (`/(UP|DOWN|BULL|BEAR)USDT$/`) and stablecoin-adjacent bases
  (`USDC, FDUSD, DAI, TUSD, USD1, PYUSD, USDG`), rank by `quoteVolume` descending, take top
  `EXTRA_PAIRS_COUNT`.
- On failure or timeout (`PAIR_RESOLUTION_TIMEOUT_MS`, default 5000ms): log a warning,
  proceed with required pairs only. Never let pair-resolution failure block startup.
- Full logic: `specs/pair-resolution-strategy.md`.

**Backpressure (ADR-B4) — exactly one mechanism, deliberately:**

- Latest-state conflation: one `PairState` per pair in an in-memory map, snapshotted and
  broadcast on each `BROADCAST_INTERVAL_MS` tick (default 100ms).
- Per-client check before each tick's write: if `ws.bufferedAmount > MAX_BUFFERED_BYTES`
  (default 65536), skip that client for this tick. Track consecutive skips; at
  `MAX_CONSECUTIVE_SKIPS` (default 10) in a row, disconnect with close code `1013`.
- **Do not add a second backpressure mechanism** (a per-client message queue, a
  time-based lag timeout, etc.). This was evaluated and explicitly rejected as redundant
  complexity — see ADR-B4's "Options considered" table. One signal, one consequence.
- No per-client message history is ever retained. Memory is `O(pairs)`, never
  `O(clients × pairs × time)`.
- Full logic: `specs/buffering-strategy.md`.

**`lastUpdatedAt` (ADR-B4, ADR §12.2):**

- Stamped with the wall-clock time of the conflation tick that produced the snapshot —
  never the raw timestamp from the incoming Binance message.

**Pressure & Spread (ADR-B5) — exact formulas, no deviation:**

```
Spread          = lowest_ask_price − highest_bid_price
Buy Pressure %  = (bid_volume_top_N / (bid_volume_top_N + ask_volume_top_N)) × 100
Sell Pressure % = 100 − Buy Pressure %          (complement by construction, not independently computed)
```

`N = ORDER_BOOK_PRESSURE_DEPTH` (default 10) — a named constant, never a hardcoded literal.
Implement in `domain/services/PressureCalculator.ts` as a pure function. Full spec:
`specs/pressure-spread-formula.md`.

**Metadata endpoint (ADR-B6):**

- `GET /pairs/meta` returns real data from `ticker/24hr`, filtered to the resolved pair
  list, cached 60s.
- Fallback on Binance outage: mock data for the five required pairs only. Additional
  pairs are simply absent during a fallback — do not mock them.

**No WebSocket heartbeat, anywhere (ADR-M6, applies to this repo too):**

- The 100ms broadcast cadence IS the liveness signal for the mobile client. Do not add a
  server-side ping/pong protocol — that was evaluated and rejected. If you think one is
  needed, that's scope creep relative to the spec; raise it, don't add it.

**Observability (ADR-B8):**

- `pino` for structured logs (info on successful pair resolution, warn on fallback).
- `@prometheus-io/client` (the official successor to `prom-client`) metrics at `GET /metrics`: `pulsecrypto_ws_connections_active` (gauge),
  `pulsecrypto_ws_messages_broadcast_total` (counter),
  `pulsecrypto_ws_messages_dropped_total` (counter — both skip and eviction),
  `pulsecrypto_ws_broadcast_latency_seconds` (histogram),
  `pulsecrypto_binance_messages_received_total` (counter),
  `pulsecrypto_supported_pairs_count` (gauge — set once at startup).

**Contracts (ADR-X1):**

- `contracts/schemas.ts` in this repo is the source of truth for wire formats. The mobile
  repo mirrors it byte-for-byte into `src/contracts/`; `pnpm run check:contracts` there diffs it
  against this repo's raw GitHub URL (there is no CI yet — ADR-X3).
- If you change a schema here, that's a breaking change for the mobile repo (its drift check
  fails) until its mirror is updated — say so explicitly when you make the change.

## Testing (ADR §8)

- Unit (Vitest): `ConflationEngine`, `PressureCalculator` (exact formula results against
  fixtures), `BinancePairResolver` (required pairs always present; exclusion filters;
  fallback on timeout/error) — all with ports mocked, no live network.
- Integration (Vitest + real Fastify app + `ws` client): REST contract and fallback, WS
  broadcast, origin allowlist — payloads checked against `contracts/schemas.ts`. The Binance
  adapters are unit-tested with an injected fetch; the failing-`exchangeInfo` fallback is
  covered at the resolver's unit level.
- Every PR needs passing tests before merge — enforced by the pre-push hook (ADR-X2), not
  just convention. CI (ADR-X3) is designed but not implemented yet.

## Working method

1. Confirm a spec exists in `specs/` for what you're about to build. If not, write it
   first, referencing the relevant ADR-B* section.
2. Implement against the spec.
3. Write tests derived from the spec's stated behavior, not from your own implementation.
4. Verify directly before calling anything done — run the build and the test suite
   yourself, don't just eyeball the code (ADR-X6).
5. Review the diff (`git status`/`git diff`), then commit with a conventional-format
   message — no AI attribution trailer. Never push or merge; that's the user's alone.
6. **Always end by giving the user exact terminal commands to independently verify what
   was just built** (install/build/test, and a live/manual check if one makes sense for
   the feature) — don't just assert it works, hand them the means to confirm it
   themselves, every time, not only when asked.
7. If something in the spec or ADR seems wrong or you want to deviate, say so and wait —
   don't implement your own alternative silently.
